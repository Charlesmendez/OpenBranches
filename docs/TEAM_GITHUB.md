# GitHub installation, refresh, and workspace explorer

The provider reader, owner authorization flow, repository catalog, reviewed selection, removal flow, background refresh coordinator, and permission-aware branch/PR explorer are connected to the running team service and browser UI. They are tested with fictional GitHub responses; no real GitHub installation has been authorized during development. Selected repositories are persisted by stable numeric GitHub ID with owner-only access by default.

The coordinator refreshes selected repositories with bounded concurrency, persists normalized branch and pull-request evidence, reports waiting/current/partial/error state, and keeps the last verified snapshot when a refresh fails. Authorized browser sessions read those snapshots in the separate `Branches & PRs` view. The existing Mac GitHub connection continues to work independently.

`team-service/src/github/app.ts` accepts a server-authorized installation/account binding and a stable numeric repository ID. It authenticates as a GitHub App, requests read-only installation access, and returns normalized repository, branch, PR, review/check, and ancestry observations. It reuses `src/github` with the desktop; there is one implementation of source parsing and evidence semantics. `src/shared/readJson.ts` provides the byte-bound decoder shared by GitHub and team API clients.

## Provider boundaries

- App authentication uses an in-memory RSA private key and a signed RS256 JWT, backdated by 60 seconds and expiring nine minutes ahead. This follows [GitHub's JWT requirements](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-json-web-token-jwt-for-a-github-app). The service reads one explicitly configured absolute private-key file into memory and never exposes it to browser or device clients.
- Repository reads mint a token explicitly limited to one numeric repository ID and read-only metadata, contents, pull requests, checks, and commit statuses. A separate catalog token requests metadata only. GitHub documents [repository and permission narrowing](https://docs.github.com/en/rest/apps/apps?apiVersion=2026-03-10#create-an-installation-access-token-for-an-app); the reader validates the returned permissions and token lifetime before using it. Tokens remain local to a read and are never returned or persisted.
- Installation ID, account ID/type, suspension, optional returned app client ID, and required permissions are checked before and after reading. The scoped token's repository catalog must contain exactly the selected ID. Repository identity is checked at the named endpoint before and after fetching work. Transfers, name reuse, permission removal, and late canceled results fail the read.
- An authorized installation is **not** evidence that a particular user may connect it to a team. The coordinator binds the flow to the initiating owner session and workspace, rechecks user or organization ownership before and after catalog reads, and accepts only repositories from the short-lived reviewed catalog. The adapter is never exposed directly behind a caller-supplied installation ID.
- Prior cached PR/history evidence is accepted only for the same stable repository ID and current full name. Partial history remains explicit; an absent entry in a bounded list is not proof of deletion.
- Requests use the fixed `api.github.com` origin, omit cookies, refuse redirects, and ignore provider-supplied pagination destinations. Error bodies and arbitrary network exceptions cannot expose tokens. The shared transport bounds decoded response bytes and applies finite rate-limit backoff.
- Each operation has a one-minute timeout and a 120-request ceiling. The catalog stops at 1,000 repositories and reports completeness. Branch pages have at most 100 entries; existing branch/PR/history/check budgets remain in force. No repository write or cleanup method exists. The only POST creates a short-lived read credential.
- Background work uses at most two readers by default and coordinates service instances with PostgreSQL advisory locks. Network requests never run inside a database transaction. A generation check drops late results after removal or reconnection; success and failure both publish a workspace invalidation without storing provider error text.

## Workspace presentation

- `GET /api/workspaces/:workspace/github/work` accepts optional project, member, search, and cursor filters. Browser sessions must belong to the workspace; device credentials cannot read it. Owners can see every active selected repository. Members see only projects explicitly granted to them.
- A person filter matches a PR author, requested reviewer, or submitted reviewer by stable GitHub user ID. It does not label that person as the owner of a branch or claim they are active now. Live activity remains sourced from opted-in Mac reports.
- Branch relationships to develop, dev, main, and master use stored immutable commit SHAs and the reader's ancestry result. The UI distinguishes `In target`, `Not in target`, and `unknown`; an incomplete or failed read never becomes a negative claim.
- Repository search covers names, branch names and SHAs, PR number/title/head/base, authors, requested reviewers, and teams. Repository cards use progressive disclosure and switch between PR and branch evidence. PR rows expose author, head/base, update time, draft/closed/merged status, saved-history status, review requests, check summary, and the verified GitHub URL.
- The service returns at most 10 repositories per page and at most 200 matching branches and 200 matching PRs per repository. The browser combines no more than 10 consistent-revision pages or 16 MB, shows omitted counts, and asks the user to narrow filters at the bound.
- Workspace invalidations and manual refresh reload both the local report view and the GitHub view. The browser keeps the two evidence sources separate so published GitHub state is never presented as proof of current local activity.

## Prioritized attention

- Each successful repository refresh persists a bounded attention projection beside the normalized snapshot. The projection produces at most one finding per PR while preserving every matching signal: current failed checks, current requested reviewers or teams, drafts without updates for seven days, and merged PRs whose exact head name and immutable SHA still exist as a published branch.
- A failed check outranks other signals on the same PR. A review request for the signed-in GitHub identity ranks ahead of general review work, followed by quiet drafts and exact merged-branch cleanup. Age alone never implies that an ordinary PR should close, and a reused branch name with a different SHA is not a merged-branch copy.
- `GET /api/workspaces/:workspace/attention` is browser-only and uses the same owner/project-grant boundary as the repository explorer. Results can be narrowed by queue, signal, project, or search. The server returns at most 100 detailed findings and explicitly reports lower-ranked findings outside that bound.
- Snooze, dismiss, restore, and bulk choices are private to the signed-in member. They do not modify GitHub or Git. Every mutation revalidates the finding ID and semantic evidence revision in one transaction; changed evidence returns the finding to review instead of silently applying an old choice. A snooze lasts seven days. Removing the GitHub selection deletes its saved decisions.
- The first panel is deliberately small and decision-oriented. Its four signal totals, padded queue tabs, exact selection count, evidence text, observation time, and project filter lead into the complete branch and PR explorer below it.

## Evidence and remaining work

`team-service/tests/github-app.test.ts` verifies generated JWT signatures, read-only token scoping, normalized branch/PR/check/ancestry output, secret/body omission, identity changes, suspension, permissions, cancellation, reused names, retained PR history, and partial catalog bounds. `team-service/tests/github-setup.test.ts` covers the session-bound OAuth return, owner authority, reviewed catalogs, tenant isolation, stable selections, refresh persistence, failure retention, concurrent removal, restart persistence, host-key loading, the permission-scoped work view, attention decision isolation and revision checks, exact target state, person and `#number` filtering, private-data omission, browser-session access, and device rejection. `tests/team-attention.test.ts` proves the projection rules and rejects stale or ambiguous evidence. `tests/team-client.test.ts` verifies encoded filters, bulk commands, and response scope. `tests/github-work-pages.test.ts` verifies revision-consistent pagination, one restart after a changing snapshot, and a bounded failure when the revision keeps changing. Tests generate an ephemeral RSA key and use fictional repositories; they do not use a real app or GitHub organization.

Next: extend the prioritized company view to local-only and apparently forgotten opted-in work, then add organization membership synchronization. Webhook-assisted refresh, live GitHub acceptance, and real two-member/device verification remain release requirements. Do not interpret the fictional preview as completed production acceptance.
